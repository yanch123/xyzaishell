# 架构设计

本文是文档阶段的实现讨论基线。产品约束以[需求](requirements.md)为准；技术栈、模块命名、状态命名和数据结构属于建议设计，尚未编译、集成或压测。接口细节见[接口](interfaces.md)，配置与凭据规则分别见[配置](configuration.md)和[安全](security.md)。

## 1. 核心约束

1. 每个独立应用实例只管理一个活动 SSH 连接、一个可见交互 PTY。
2. 用户和 AI 使用同一 PTY；没有 AI 专用的后台 exec 或本地命令执行通道。
3. 同时只有一个 AI 任务拥有写入权；手工输入始终由用户自行协调。
4. 传输字节的串行化是工程一致性措施，不提供人/AI 命令语义隔离。
5. 模型负责生成提案，宿主负责授权、凭据、状态与真实 I/O。
6. 不确定的完成、交互、风险或发送结果进入 unknown/需用户确认；不能靠超时猜测成功或重发。
7. 复杂判断与 Jev 实现延后，只保留可插拔接口。首版不以通用 shell 集成为前置条件。

| 层 | 建议组件 | 负责什么 | 必须验证什么 |
| --- | --- | --- | --- |
| 桌面壳 | Tauri 2 | 窗口、WebView、受限 IPC、Windows 打包 | 实際 Windows 构建、安装、权限配置、WebView2 策略 |
| UI | React + TypeScript | 分栏、聊天、设置、状态与授权视图 | 渲染开销、输入焦点、Unicode/输入法、事件背压 |

Tauri 允许 Web 前端与 Rust 宿主组合；xterm.js 是终端前端，SSH 和真实执行仍由宿主提供。[Tauri 官方介绍](https://v2.tauri.app/start/)；[xterm.js 文档](https://xtermjs.org/docs/)。

Eugeny/russh 是面向 Rust/Tokio 的异步 SSH 库；Rig 提供 Rust 中的模型与 agent 运行能力。这些能力支持上述选型方向，但不证明组合在本项目中已可用。[russh 官方仓库](https://github.com/Eugeny/russh)；[Rig 官方仓库](https://github.com/0xPlaygrounds/rig)；[Rig 文档](https://rig.rs/docs)。

不在本文锁定依赖版本，也不使用未经测试的包体积、延迟、内存或兼容性数字。后续原型通过后，再提交锁文件及实测矩阵。Windows 安装器还须决定 WebView2 缺失时的处理方式，不能假设所有机器都已满足依赖。[Tauri Windows 安装文档](https://v2.tauri.app/distribute/windows-installer/)。

## 3. 进程与模块

```text
一个 xyzaishell 实例
  ├─ WebView UI
  │    ├─ 左：xterm.js 可见终端
  │    └─ 右：聊天 / 任务 / 命令卡片 / 授权 / 设置
  └─ Rust 宿主（状态和能力的权威来源）
       ├─ Session Supervisor ─ SSH Adapter ─ 单一 SSH PTY ─ 远端 shell
       ├─ PTY Write Queue（AI 与手工的有序发送入口）
       ├─ Task Registry + AI Writer Lease
       ├─ Execution Gate + Approval Store
       ├─ Rig Runtime Adapter ─ 选定的模型目的地
       ├─ Decision Provider Port（首版 unknown 回退，未来可接 Jev）
       ├─ Terminal Observation + Context Builder
       ├─ Credential/Task Secret Resolver
       └─ Config / 非秘密记录 / 有界事件流
```

该图描述逻辑责任，不要求每个方框单独运行线程或进程。多个应用实例分别具有自己的 SSH 状态、任务集合、写入权与事件命名空间。即使两个实例连接同一服务器，也不承诺协调它们的远端副作用。

### 3.1 UI 边界

- UI 只发出窄化的意图，如发送手工输入、启动任务、批准某次操作、调整 PTY 尺寸。
- UI 不能任意指定本地 shell、读取任意文件或直接获得软件管理的密钥明文。
- 终端字节交给终端仿真器处理；聊天/Markdown 渲染单独消毒，不能把终端输出作为可执行 HTML。
- Tauri capabilities/IPC 权限应按最小必要能力配置；不因调试方便开放通用 shell、文件系统或任意网络工具。
- 真实操作状态来自宿主事件，不以按钮的乐观 UI 状态替代。

终端输出与链接处理均有安全边界；详细限制应结合 xterm.js 安全指南验证。[xterm.js 安全指南](https://xtermjs.org/docs/guides/security/)。

### 3.2 Session Supervisor / SSH Adapter

一个宿主所有者管理连接、认证、PTY 建立、输出接收、尺寸变化和关闭。SSH Adapter 不知道模型提示词，只处理已经通过宿主检查的操作。

- 新连接分配新的 `session_id`；同一连接重建 PTY 或重连时更新代次，旧引用不能继续写入。
- 主机密钥验证先于建立可信连接；认证失败不回退为跳过验证。
- 只向运行时暴露单一受控 PTY 能力，不暴露 exec/subsystem/第二会话入口。
- SSH 数据写入成功只说明发送路径接受了字节，不能据此得出远端命令成功。

### 3.3 Rig Runtime Adapter

Rig 负责模型会话、多轮推理和工具提案；不把 Rig 的 agent 自循环当作宿主授权器。

运行时可持有任务的非秘密上下文、系统约束和工具定义。所有工具回调进入 Execution Gate，并获得结构化结果，如「等待批准」「缺少密钥」「结果未知」。重复或重新生成的工具提案不会自动继承旧批准。

模型 API Key 由宿主 Provider 适配器按批准的 Base URL 附加到请求认证层，不出现在模型内容、工具 schema 示例、命令卡片或异常文本中。

## 4. 两种写入约束，不能混为一谈

### 4.1 PTY 传输串行化

所有入站写入请求最终经过同一个有界发送队列。队列保证宿主按确定顺序处理数据块，不会让多个异步任务同时修改同一缓冲/通道状态。

这不等于 shell 事务：用户可能先输入半条命令，AI 随后发送包含回车的命令；用户输入也可能被前台程序消费。单个数据块在传输中的顺序无法消除这些语义混杂。产品不增加手工优先/暂停/恢复状态机来解决它，用户需要自行避免冲突。

### 4.2 AI Writer Lease

`AI Writer Lease` 只回答「哪个 AI 任务可申请当前 PTY 写入」。多个聊天可以保留或生成回复，只有持有者可提交会改变 PTY 的操作。

建议规则：

1. 写入权绑定实例、会话代次和任务，获得权利不等于任何具体操作已获批准。
2. 切换聊天不会转移权利；新任务写入需明确获得权利。
3. 每次真正写入前检查持有者、当前提案批准与会话身份。
4. 一个步骤的写入结果或远端状态未知时，保持后续 AI 写入阻塞；不能通过把写入权转给另一个任务绕开未知状态。
5. 停止、完成或显式交接可以结束本任务的持有关系，但新的任务仍需确认当前 PTY 可用于其下一步。
6. 手工输入不申请该 Lease，也不因为按键而自动修改 AI 任务状态。

队列接受请求与最终发送之间可能有状态变化，因此检查应尽量靠近发送点，并拒绝过期代次/提案。不能承诺用户手工输入与 AI 写入间的 shell 原子性。

## 5. 状态模型

具体状态枚举、字段及迁移约束统一以[接口契约](interfaces.md)为准。本节说明必须分开的状态维度，不定义第二套代码枚举。

### 5.1 连接状态

连接经历未连接、连接中、主机验证/认证、已连接和关闭等阶段；任何阶段都可失败。已连接只表示传输/PTY 已建立，不代表 shell 空闲。

### 5.2 终端观测状态

| 状态 | 含义 | 可否自动发下一步 |
| --- | --- | --- |
| 未知（unknown） | 当前前台程序、输入位置或上一操作结果缺乏充分证据 | 暂停依赖该判断的写入，等待用户确认/处理 |
| 当前可输入已获确认 | 在明确范围内有可追溯依据认为可接收下一项操作 | 仍需写入权、风险与授权检查 |
| 等待观测 | 已发送某次操作，正在收集后续事件 | 不将静默直接视为完成 |
| 存在输入请求 | 有具体交互请求及其来源信息 | 只有目标、内容和权限均明确时才能响应；否则询问 |
| 已关闭 | PTY 已关闭或连接断开 | 不发送 |

上述是逻辑状态描述。“当前可输入已获确认”的证据可以是用户对当前状态的明确确认；未来也可来自已验证的受支持 shell 适配器。提示符启发式或模型建议不得自行升级为可靠事实。用户确认的有效范围与限制应显示，不能作为对未来全部步骤的永久保证。

首版无需通用 TUI 检测、命令边界推导或远端注入脚本。无法确认时保留 `unknown` 是可接受结果；自动化程度会因此受到限制。

### 5.3 任务状态

任务需要表达：尚未运行、规划中、等待 AI 写入权、等待授权、等待密钥、执行/观察、需要用户处理，以及完成、停止或失败。具体枚举和允许的迁移由接口契约定义。

任务状态与终端状态独立。例如：

- 任务已经停止，远端命令仍可能在执行，终端仍是未知。
- 任务正在等待授权，用户仍可手工输入，终端环境可能已改变。
- 聊天 A 完成不代表聊天 B 的目标达成，也不代表远端 shell 已回到原目录。
- 失败状态应保留已观察事实；「网络失败」不能改写成「远端操作未执行」。

### 5.4 操作发送状态

每项操作至少区分提案、获批、排队、开始发送、已发送和结果观测。崩溃或网络错误可能发生在任意相邻状态间，持久化状态不可能为远端副作用提供 exactly-once 保证。

只要不能证明操作未发送，恢复时按发送结果未知处理；不自动重放。能证明未发送的排队项也需重新检查会话、授权和上下文，不能跨新连接直接续写。

## 6. 为什么 SSH PTY 不能提供完整命令结果

SSH 协议提供 session、PTY 请求、shell/exec 请求、数据和通道结束等机制。对于交互 shell，客户端收到的是持续会话数据；通道级退出状态不等同于在该 shell 中每输入一条命令的独立退出码。这是基于协议机制的设计判断。[RFC 4254 §6.2、§6.5、§6.10](https://www.rfc-editor.org/rfc/rfc4254)。

因此：

- 命令后出现几行输出，不证明它完成；没有输出，也不证明它没有执行。
- 后台进程、手工操作及控制序列可能影响同一观察窗口。
- 退出码应允许缺失；没有可信来源时不得填 `0`。
- 延时等待只能控制观察预算，不能定义「成功」；超时应报告等待超时/未知。
- 不为了得到漂亮的结构化结果而隐藏地改用 exec 通道。

后续可以为明确支持的 shell 增加可选边界/状态适配器，但须单独验证、明确适用条件与未知回退。首版不承诺注入标记、修改 prompt 或任何通用适配协议。

## 7. 主要数据流

### 7.1 建立连接

1. 用户选择连接配置；宿主只读取该连接需要的认证材料。
2. 连接并校验主机身份，完成认证，申请 PTY，建立交互 shell。
3. 创建会话代次，开始有序事件流，把真实输出交给终端显示。
4. 终端初始可用性仍按可获得证据决定；若未知，用户确认后才能开始依赖 shell 就绪的 AI 步骤。

### 7.2 AI 自动执行

1. 用户在某个聊天下达目标；宿主复用该聊天稳定的 task_id 与任务配置，建立本次 run_id 和当前模型配置快照。
2. Context Builder 选择有限且脱敏的任务/终端信息；确认模型目的地后交给 Rig。
3. 模型生成操作提案。宿主分配操作标识，显示可审查内容。
4. Execution Gate 检查会话、写入权、风险、必要批准、输入目标、密钥引用和资源预算。
5. 任何必要信息未知时返回 `needs_user`；通过后才将该操作交给 PTY 队列。
6. 收集真实输出、发送状态及证据；向模型和 UI 返回同一事实基础上的结果。
7. 运行时继续规划或结束。超过循环/输出预算则暂停并说明原因，不无限自循环。

基础风险检查必须留在宿主。未来 Decision Provider 能帮助解释上下文，但不获得直接执行能力。

### 7.3 缺失任务密钥

1. 提案只引用某任务的指定密钥名。
2. 宿主发现该键缺失，向本机 UI 显示用户应编辑的任务文件位置；模型只收到缺失键名，不得到路径、文件内容或其他密钥。
3. 聊天提示补齐文件；用户编辑完成后主动重试/继续。
4. 宿主重新验证文件、任务归属、用途、目的地与当前授权。
5. 在执行边界解析所需密钥；不能确定输入会交给谁时停止，不能盲目向 PTY 写入密码。

任务文件中的存在性不构成使用授权。私钥路径属于 SSH 配置，不从任务密钥文件找替代值。

### 7.4 拒绝、停止与恢复

- 拒绝授权：操作保持未执行，运行时可解释或提出不同方案；不同方案重新审核。
- 停止 AI：取消尚未执行的规划/待发送步骤；已发送部分如实记录。中断远端进程是另一项动作。
- 断线：停止 AI 写入，保留已观察内容，未确定的操作标未知。
- 重连/重启：新建会话身份；允许查看任务记录，不自动恢复执行或重放密钥/命令。

## 8. 上下文、事件与持久化

### 8.1 事件事实与屏幕快照分开

宿主事件建议携带实例、会话代次、单调序号、时间、来源和可选任务/操作标识。来源描述「应用知道是谁发起写入」，不表示能唯一归因远端输出。

UI 的当前屏幕、有限原始输出片段、模型可读文本和审计元数据是不同视图。ANSI/控制字符解析、换行、覆盖屏幕与宽字符处理可能损失信息；应保留范围与缺口标记。

### 8.2 三类配置与存储边界

| 数据 | 建议位置/管理者 | 是否进入模型上下文 |
| --- | --- | --- |
| Base URL、模型名称等模型设置 | 用户可编辑的全局模型文件 | 仅必要的非秘密能力说明 |
| 模型 API Key | 同一全局模型文件中的明文字段，由宿主受限读取 | 不进入模型内容；只用于对应请求认证 |
| SSH 主机/用户/认证方式/私钥路径 | SSH 连接配置 | 默认不整份注入；只提供任务所需的目的地描述 |
| SSH 密码、私钥内容/口令 | SSH 凭据管理与本地私钥文件 | 不提供通用读取 |
| 每任务其他密钥 | 用户可编辑的任务专属文件 | 只提供键名/是否可用，明文只在批准用途边界解析 |
| 聊天、任务及操作记录 | SQLite，限非秘密记录 | 按当前任务和预算选择 |
| 原始 PTY 数据 | 有界运行时缓冲为默认建议 | 经筛选；不可假设全部无秘密 |

模型配置和任务密钥文件按当前提案包含明文秘密，须限制本机访问并披露编辑器备份、同步与同用户进程暴露风险；它们不是加密保险库。SSH 密码/口令的 Windows 保护也不保护已被控制的同用户环境。

不要在 SQLite 中保存真实凭据或完整密钥文件。聊天、命令输出也可能含秘密；脱敏失败和未知秘密是剩余风险，因此持久化范围、清理与导出需要在安全设计中明确。左侧远端原始回显可能暴露用户或程序输出的秘密，不能声称 UI 层遮罩能阻止全部泄露。

### 8.3 有界与多实例

- 对终端缓存、IPC 队列、单次输出、上下文 token/字节、日志和循环步数设预算，具体默认值待测量。
- 慢消费者触发背压或明确的缺口事件；丢弃上下文后不能静默继续依赖缺失证据。
- 建议任务/事件按实例或工作区隔离；全局配置采用可识别修订与原子替换，避免多个进程互相覆盖。
- 配置变更不悄悄改变正在执行提案的目的地。切换生效点、修订失效规则由接口与配置契约规定。

## 9. 可插拔决策边界与 Jev 延后

Decision Provider 的最小职责是接收有限、脱敏且注明来源的判断请求，返回建议、依据、不确定性和是否需要用户确认。预留类型可包括风险说明、交互请求解释、操作完成证据评估；具体 schema 见[接口](interfaces.md)。

首版可以没有外部决策模型：基础规则处理明确情况，其他返回 `unknown`。该接口不提供密钥、原始私钥文件或绕过审核的执行句柄。

未来接入 Jev 时，另行确定：其身份与协议、运行位置、认证、可见数据、超时/故障回退及用户对新目的地的授权。当前不编造 Jev 的 SDK、HTTP 路径、返回字段、性能或能力。即使未来模型判断「允许」，最终决定仍需满足宿主硬性约束。

## 10. 故障策略

| 故障 | 对用户/任务的结果 | 不允许的处理 |
| --- | --- | --- |
| 模型超时、限流或响应无效 | 明确请求失败；保留已执行事实；按受限策略重试纯模型请求 | 自动换模型目的地、重放旧工具写入 |
| 不支持的工具调用/无效参数 | 拒绝该提案并返回结构化错误 | 猜测参数后直接执行 |
| SSH 写入一部分后断线 | 部分/未知发送结果；暂停任务 | 重发整个命令假设幂等 |
| 用户拒绝高风险操作 | 操作未执行，显示拒绝 | 拆成较小命令绕过同一授权 |
| 密钥缺失/读取失败 | 请求用户编辑该任务文件 | 搜索其他任务或全盘找密钥 |
| 终端状态、输入目标不明 | 暂停依赖该判断的步骤 | 猜测密码提示、自动回车/输入秘密 |
| 输出超预算/事件缺口 | 标记截断范围并暂停受影响判断 | 将摘要当作完整输出或成功证据 |
| 记录存储故障 | 显示记录能力受限；关键授权/状态无法可靠记录时停止相关 AI 发送 | 宣称审计完整并继续不受控写入 |
| 宿主崩溃后重启 | 历史可查看，未决操作为未知，新会话重新检查 | 自动续跑、跨会话复用批准 |

## 11. 许可与后续验证

候选依赖中，russh 官方仓库标示 Apache-2.0，Rig 官方仓库标示 MIT。其他直接/传递依赖仍需对锁定版本逐项核查；不能从候选栈推导「没有许可证问题」。[russh](https://github.com/Eugeny/russh)；[Rig](https://github.com/0xPlaygrounds/rig)。

项目自身许可证尚未决定。公开仓库与允许任意使用/再分发不是同一个决定；发布实现前应确认项目许可及依赖通知。

后续技术验证至少覆盖：

1. 候选版本在 Windows 10/11 x64 的构建、打包、安装与卸载。
2. 同一可见 PTY 的手工输入、AI 输入、resize、Unicode、粘贴及输出背压。
3. 两个 AI 任务写入竞争、排队失效与会话代次检查。
4. unknown/用户确认路径，不依赖强制 shell 集成也能安全停止。
5. 高风险拒绝、凭据引用、目的地变更、断线/崩溃不重放。
6. 多实例配置/记录隔离，以及真实模型的工具调用和取消语义。

这批验证将决定建议栈是否保留，并给出明确的支持范围。当前文档未声称以上任何运行测试通过。
