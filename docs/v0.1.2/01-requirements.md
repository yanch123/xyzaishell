# 01 — v0.1.2 需求与范围

状态：待评审的设计草案；本轮仅文档，不代表已实现。

## 1. 用户目标与设计原则

用户希望像使用传统桌面 SSH 软件一样管理服务器和设置模型，无需先理解配置文件、存储后端和内部状态机。主工作区仍是左终端、右 AI；界面减少重复说明和普通通知弹窗，同时让真正需要决定的事项清晰可见。

本轮整理的需求方向（具体交互细节仍待评审）：

- 独立 Settings 入口，直接编辑 Base URL、API Key、模型名，支持“保存”和“保存并测试”，测试使用已保存配置；TOML 交由程序维护，路径与环境变量放在高级区。
- SSH 连接和档案管理统一；能够保存并连接，用户可选择记住密码并知晓本机保存风险。
- 保存服务器资料不等于必须保存密码；未保存凭据时应在连接时询问。
- 修正全局、单向的 `session_only` 体验；安全存储不可用时仍可保存资料并临时认证。
- 普通状态和可展开的详细说明集中到底部；保留主机密钥、高风险命令、未保存修改等必要决策。
- Windows 与 Linux 都在范围内；一个进程一个 SSH 连接，多进程独立窗口，不增加 SFTP。
- 设置和日志查看采用非模态界面；新服务器启用新对话，日志按连接／服务器／会话分组。
- 普通命令正常路径自动执行，危险命令才进入风险批准，未知风险不自动放行；使用当前 Shell 临时 hooks，优先 Bash。

菜单分组、工具栏按钮、列表双击与右键操作、消息面板分页方式、接口名称属于本轮提案，需评审后落实。借鉴成熟客户端的交互习惯，不新增完整会话树、标签页或全部 Xshell 功能作为隐含需求。

## 2. 功能需求

### R1 — 主窗口信息结构

- 保留左终端、右 AI 的主要空间；提供清楚的菜单、常用操作工具栏及已保存连接入口。
- 已保存连接列表可选择、连接、编辑、重命名、删除；双击连接、右键菜单和键盘等效入口为建议交互。
- 底部状态栏显示 SSH、模型配置和待处理事项；展开消息面板查看时间、来源、概要、错误码、帮助及恢复操作。
- 不因普通完成通知、重连状态或帮助说明打断终端输入，不让面板反复抢占焦点。

### R2 — 模型设置

- 新用户可在软件内完成配置；已有配置可编辑非秘密字段，保存时不必重新填写未更改的 Key。
- Key 输入仅用于新建或替换；后端不向前端返回已保存 Key，也不把占位星号当作真实值保存。明确提供“保留”“替换”“清除”的意图。
- Base URL 指向新的请求目标时，不静默携带旧 Key 或沿用旧接收方授权。使用旧 Key 必须显式选择，并在发请求前确认新的目标和数据范围。
- “保存”只保存配置；“保存并测试”先保存再对该已保存版本发送明确说明的最小测试请求，不携带聊天、终端、任务秘密或 SSH 凭据。测试成功不等于工具调用已兼容。
- 高级区显示实际文件路径、环境变量覆盖、重新加载和相关帮助。保留现有 TOML 的高级字段和路径语义，不要求普通用户手工编辑文件。
- 模型 Key 仍可能以明文保存在现有受限 TOML；在相关帮助和首次保存提示中说明，不增加每次连接的冗长确认。

### R3 — 统一 SSH 连接与档案管理

- 一个编辑器管理名称、主机、端口、用户名、密码或私钥认证、私钥路径以及凭据保管选择。
- 新建以“连接”为主按钮，配合“保存连接”和“记住密码／私钥口令”选择；编辑已有档案用“保存／取消”，不混入隐式连接。保存成功与连接成功分别报告。
- 档案可只保存非秘密资料。密码认证缺少凭据时，连接流程询问密码；私钥认证只在需要口令时询问，不强迫无口令私钥填写虚构值。
- “记住密码／私钥口令”是当前档案的明确选择。新档案默认不保存秘密；编辑已有档案时默认保留其现有保管选择和凭据。
- 连接过程中防止重复点击导致多次认证；取消、失败和关闭后清除短期输入。提供手动重新连接入口，仍受单 SSH 约束，不自动重试或重放命令。
- 改动档案不会改变已经建立的 SSH 会话；已有连接时，另一目标默认在新进程窗口连接，不默认断开当前会话。只有明确“在当前窗口切换”才处理旧连接和 AI 任务。

### R4 — 逐档案凭据策略与恢复

- 区分“保存档案资料”“该档案是否持久保存秘密”“本次临时提供秘密”三个概念，不再用一个全局 `session_only` 同时控制它们。
- 同一实例可以列出记住密码和每次询问的不同档案，修改一个不移除其他档案的秘密。
- Windows 保持 DPAPI CurrentUser；Linux 保持 Secret Service。后端锁定、缺失、访问拒绝分别可见，不能默默回退明文。
- 安全存储不可用时，允许只保存资料或明确临时连接；不能把“记住密码”失败显示成全部成功，也不能丢弃原有凭据引用。
- 对旧全局 `session_only` 数据提供可恢复迁移。已经丢失的密码不能恢复；用户重新填写后可为单个档案启用系统保护保存。

### R5 — 反馈、帮助与必要决定

- 表单字段错误就近显示；普通成功、故障和状态变化进入统一消息面板，提供相关操作或帮助。
- 一项操作有明确的当前状态，不因多个入口出现相互矛盾的成功与失败提示。
- 首次或变化的 SSH 主机密钥、AI 高风险／不确定命令、数据接收方变化、丢弃未保存修改以及删除资料等实际决定继续使用显式确认。
- 未知结果不报成功，不自动重试不确定的保存，不自动重发远端命令。通知已读或清空显示记录不等于批准操作。

### R6 — 数据与安全边界

- API Key 仅作为目标模型服务的认证信息；SSH 密码／私钥口令仅用于对应 SSH 认证。它们不得作为模型上下文、工具结果、普通事件或诊断日志内容。
- 新增 UI 不改变三类配置的隔离，也不允许模型调用设置、凭据保存或审批接口。
- 保留受限目录、权限校验、并发修订检查和可核对的保存结果。不得使用浏览器 localStorage 保存秘密或完整认证表单。
- 日志与错误只包含必要的脱敏信息；承认同用户恶意进程、内存转储、远端回显及未知秘密变形等剩余风险，不承诺绝对防泄漏。

### R7 — 兼容与迁移

- 保留原档案 ID、标签、服务器资料、有效平台凭据，以及独立的 known_hosts、聊天和 Shell 日志。
- 不兼容的连接配置改动使用明确版本升级，不能以相同 schema 静默重解释旧数据。
- 迁移不会自动连接、调用模型、恢复审批或重新发送命令；失败不覆盖唯一可用旧数据。
- Windows/Linux 的真实后端行为、旧数据升级和安装后操作分别验收，不能用网页预览或同版本重装替代。

### R8 — 本轮交付约束

- 只新增或修订本目录下的编号设计文档。
- 不实施界面、后端、迁移或测试代码，不改应用版本，不修改历史标签、Release 或安装包。
- 不将接口草案标为已冻结，不将待执行测试标为已通过。

### R9 — AI 目标与上下文

- AI 面板头部显示当前服务器和账号，来源历史另行标注；新服务器使用新对话，不默默复用旧服务器的终端上下文。
- 查看历史不自动连接、发送上下文或恢复执行；显式沿用历史时重新核对来源、目标与数据授权。重连不恢复旧动作或批准。

### R10 — 日志范围

- 当前终端入口默认看当前会话，连接档案入口看其历史／离线记录，顶层“查看”可看全部；记录保留采集当时的主机、端口、账号和会话身份。
- 档案改名或更换目标不改写旧记录；同档案不同目标分组展示。旧记录没有可靠档案 ID 时保持未知，不按同名或地址猜造关联。
- 执行状态与可选日志独立；日志关闭、暂停或写入故障不关闭正常执行追踪。

### R11 — 自动执行与当前 Shell

- 使用当前 Shell 临时 hooks，保留原 alias、prompt 和可兼容的 hooks，不改启动文件，不切入干净子 Shell；优先支持经验证的 Bash。
- SSH 已连接不证明 Shell 空闲；安装前需要受支持的就绪契约或一次首次确认，不能盲注入 OTP／登录程序。正常命令有可靠生命周期关联时不逐条询问就绪。
- 普通／危险／未知风险分类需重新设计；复杂作用无法判断时不自动执行，不能只移除 UI 确认。授权仍由本机绑定确切动作和会话，远端事件不能授权。
- 生命周期缺失、交互、嵌套 Shell、断线等保持未知并暂停自动派发；不以静默判完成，不自动重发。手动与 AI 输入仍由用户自行协调，不新增自动接管锁。
- 具体语义与兼容边界见 [07 — 自动执行与当前 Shell 集成](07-auto-execution-shell-integration.md)。

## 3. 明确不在本版范围

- 单进程多 SSH 连接、服务器标签页、SFTP、文件传输、本机 Shell、PowerShell 或 WSL。
- 导入第三方客户端会话、云同步、跨机器明文凭据导出、完整密码管理器。
- 更换模型协议、增加代理体系、自动选择服务商、把模型 Key 迁入新的系统保险库方案。
- 自动接受主机密钥、取消风险批准、无人值守恢复 AI 执行、自动重放失败命令。
- 全面重写日志／聊天存储、将全部终端输出默认记入日志、任意 Shell／提示符插件的兼容保证；本版只增加所需身份范围和集成变更。消息面板仍是应用反馈入口。

## 4. 完成标准

新用户无需手工编辑文件即可配置模型和连接 SSH；老用户保留资料并能恢复每档案的记住密码选择。主要成功路径简短，失败路径能说明“哪里失败、哪些已经保存、下一步是什么”。上述体验通过 [05 — 迁移与测试计划](05-migration-and-test-plan.md)的对应场景验证后，才能声称实现完成。
