# 04 — v0.1.3 测试与分阶段交付

状态：验收计划，**各用例的实际执行结果及限制以开发记录和精确提交的 CI 证据为准**。本文件不记录假定通过的数量，不沿用 v0.1.2 的通过结论证明新代码。

## 1. 验收原则

1. 先验证优先功能“事实与步骤摘要”，再完成选段、终端工具和诊断的整合。
2. 正常流程与错误、重连、取消、旧结果、重复点击同等重要；安全边界不能只靠 UI 文案。
3. 为每个验收记录精确提交、命令、系统、退出状态及证据路径。聚焦用例通过不等于全套通过。
4. 分开描述纯函数测试、模拟模型／SSH、真实受控 PTY、浏览器 UI、原生安装和真实外部供应商。互不替代。
5. 本版模型能力诊断本身只发送合成测试，不执行 SSH。现有受控 SSH 回归可继续验证执行体系，但不能把诊断测试实现成远端命令试跑。
6. 不使用真实密码、API Key、用户业务输出或任务秘密作为 fixture；报告和截图也不得包含这些内容。

## 3. F2 选段分析验收

| 编号 | 场景 | 必须观察到的结果 |
| --- | --- | --- |
| S01 | 无选择／只有空白 | 不发送；不能退而读取整个终端 |
| S02 | 选择后打开预览 | 展示精确来源和可编辑文本，网络／SSH 写入计数均不增加 |
| S03 | 修改文字或分析问题 | 标记用户编辑；旧本次同意失效，发送内容是重新核对后的最终文本 |
| S04 | 取消／关闭／重复打开 | 没有自动请求；旧预览不在后来恢复为已批准 |
| S05 | 正常确认后发送 | 只进入普通聊天；保留来源标签和声明的上下文；agent.start 与 SSH 写入均未调用 |
| S06 | 换聊天、旧目标聊天、恢复历史 | 不能跨来源发送或绕过只读状态 |
| S07 | 预览中断线、同目标重连、切换目标 | generation fence 阻止旧选段沿用确认发往新现场 |
| S08 | 保存／重载模型或更换地址／模型 | 旧 revision／destination 确认失效，旧回调不得将选段投向新模型 |
| S09 | 普通聊天已经同意接收方 | 仍需要终端选段本次确认 |
| S10 | 8192 字节／200 行边界、中文、emoji | 边界行为准确；截断明确提示且字符合法；超限编辑不发送 |
| S11 | 选段含转义序列、伪造系统指令、命令、秘密 | 视为文字数据；已知秘密脱敏；不会执行或打开链接 |
| S12 | AI 任务占用、满聊天、连续双击、发送异常 | 尊重占用与容量；单次提交；未知结果不自动重发 |
| S13 | 两个聊天各有草稿 | 草稿隔离，每聊天最多一份，不写入终端偏好存储 |

建议覆盖 `TerminalPane`、`ChatPane`、聊天 hook 与现有模型调用 fixture 的集成测试；只断言按钮禁用不足以替代发送函数最后一次状态校验。

## 6. 跨功能回归

在当前执行安全用例基础上至少检查：

- 一个进程只拥有一个 SSH 会话与可见 PTY；另一目标按原规则开独立进程。
- 一个 PTY 只有一个 AI 任务写入者；选段、搜索、复制和诊断不抢占所有权。
- 动作展示、危险单次批准、过期批准、旧 generation、未知发送结果不重发。
- 用户手动输入仍由用户管理竞争；停止 AI 与发送 Ctrl+C 的效果不混淆。
- Shell 识别与操作日志独立，恢复历史不触发模型请求或命令重放。
- 模型配置保存、API Key 更新、文件冲突、秘密脱敏和连接凭据原有用例不回退。
- 旧快照缺少新字段时能安全展示，不编造上下文、结果或同意。

## 7. 执行命令与证据层级

以下命令来自现有仓库工具链，**列出不等于已经运行**。先按仓库要求准备依赖及第三方 notices，再执行与最终变更有关的全套检查。

按 CI 的实际环境继续执行受控 OpenSSH、当前 Shell PTY、平台秘密存储、Windows／Linux 打包及安装检查。已有入口包括 `.github/workflows/ci.yml`、`.github/workflows/native-acceptance.yml`、`.github/scripts/openssh-test.sh` 和 `crates/xyz-core/tests/shell_log_pty.py`；最终文件名与工作流须在提交前核对。

每项状态只能写为：通过、失败、未运行、环境阻塞或已知限制。报告需说明：

- 测试的是哪个精确提交，后续修改是否使之前证据失效。
- 是否仅在 Linux 容器完成单元／浏览器检查。
- 是否完成 Windows 与 Linux 原生快捷键、剪贴板、搜索与设置验收。
- 是否使用模拟模型；未测试的真实服务不能宣称兼容。
- 原生安装包是否构建成功、实际安装／启动过，以及产物的版本和校验信息。

真实外部模型检查必须使用界面同意的具体模型与合成范围；不得为了验收把用户的真实终端内容发给供应商。

## 8. 分阶段 dev 交付

每个阶段通过其适用检查后提交并推送 `dev`，核对远端精确提交；不得只留本地修改或把“推送发起”当作“远端已更新”。本文件本身只制定计划，不声称任何提交已推送。

1. **设计基线**：本目录 00–04 文档；四项范围、接口和反向用例对齐。
2. **优先任务上下文**：宿主事实、有限证据、模型摘要与步骤、每轮携带和 UI；先完成隔离与脱敏测试。
3. **选段与终端工具**：来源固定的可编辑预览、本次同意、普通聊天发送；搜索、字号／回滚、复制粘贴及会话 fencing。
4. **能力与 Shell 诊断**：两类模型测试、支持／不兼容／未判定结果、具体 Shell 原因；合成测试证明无工具执行。
5. **整合回归**：针对最终整合提交跑完整检查，记录原生平台和外部兼容性尚未验证的范围。
6. **使用与候选发布**：实现核验后更新使用说明、版本及相应候选产物。主 README 只写真实可用操作和限制，不塞设计流水或未经验证的功能承诺。

可以并行开发独立模块，但发布前需按同一精确提交复核所有接口与证据。阶段记录建议另建在本目录下的 `development/`；真实发布验收记录放 `release-evidence/`。没有实际记录时不先创建“通过”占位文件。

提交到 dev 不等于合并 main、打标签、正式发布或部署。公开发布继续遵循已有授权和发布流程。旧版本文档不重写为新版本行为。

## 9. 完成标准

四项功能和负向边界全部有对应实现与实际测试记录；重要失败已修复或明确列为阻塞；最终提交已在 dev 可核对；支持平台的构建和原生验证范围清楚；使用文档与实际功能一致。

若只有模拟测试通过，应明确交付“开发实现及模拟验证”，不能称“Windows／Linux 全面验收完成”。若真实模型或桌面环境不可用，保留明确未验收项，不编造外部兼容性、安装或用户验收结论。
