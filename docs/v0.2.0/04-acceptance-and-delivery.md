# 04 — 验收、迁移与分阶段交付

## 1. 文档状态与验收原则

1. 本文是 v0.2.0 的未来实现和验收计划，不代表功能已实现、测试已运行或版本已发布。本轮只交付设计文档，不改应用代码、版本号、锁文件、发布工作流或正在独立进行的 v0.1.4 发布。
2. 范围是自动／手动上下文压缩、模型／快速两种压缩方式、上下文用量和分类占比的简洁界面。默认自动压缩采用模型方式；快速方式不访问模型。具体状态机、默认值和字段以本目录架构／交互文档为准；实现前锁定一致版本，测试不得自行另设默认值。
3. 原始历史、供下一轮使用的活动上下文、单次模型请求、已捕获的有界输出是不同对象。压缩成功只改变活动上下文，不等于删除历史、恢复任务、完成用户目标或获得执行权限。
4. 每项结果必须记录精确提交 SHA、平台、测试夹具版本、命令、结果和必要证据；状态区分通过、失败、阻塞、未运行、不适用。计划中的断言不能写成已通过。
5. 模拟供应商、浏览器 mock、真实终端、真实外部模型分别报告。模拟通过可证明协议和失败处理，不能证明真实模型摘要质量、供应商兼容性或真实 token 计量。

## 2. v0.1.4 基线与回归边界

1. 现有 `task_context` 摘要限制是 1024 个 UTF-8 字节，序列化任务上下文为 32 KiB；不能把字节上限写成字符或 token 上限。单轮任务 prompt 原有 60 KiB 字节上限；v0.2.0 将该固定规划上限替换为中心模型 token 预算和经审计的最终编码请求 1 MiB 传输字节护栏；必须先通过跨块秘密匹配、UTF-8 边界、JSON 编码与完整请求脱敏审计，不得只删除旧检查。不再让 60 KiB 固定值掩盖模型真实容量。
2. 聊天当前最多 128 条消息／256 KiB，满时拒绝继续。新 run 重建运行上下文，旧摘要不是自动续跑机制；命令证据存在只取前 16 条的限制。v0.2.0 退役该全局发送拒绝限制，128 条／256 KiB 只可作为分页参考；以新账本／活动窗口和独立有界历史保留解决瓶颈，不能只增加常量后称为压缩。
3. 单 action 输出窗口 1 MiB、单 run 输出总量 8 MiB，以及 UTF-8 偏移、脱敏、`earliest_offset`、`gap`、截断提示维持原有安全语义。压缩不恢复已经淘汰的输出，不把摘要伪装为原文。
4. 实际通用工具循环是每批最多 16 次、运行累计最多 256 次模型规划响应。压缩不重置这两项预算；新增压缩请求须有独立、有限的调用／输入预算，并与主规划调用分别计数，不得借压缩无限延长运行。
5. 回归覆盖原有危险命令审批、PTY 完成与独立就绪、取消、提交去重、结果未知、日志和历史设置、跨聊天隔离。无需也不得借本版本暗中加入“重启后自动继续历史会话”或自动重放命令。

## 3. 确定性核心与快速压缩测试矩阵

1. **Q01：确定性与零模型。** 同一已脱敏账本、策略版本和预算生成相同保留项、摘要元数据及引用；固定种子随机测试可复现。网络／模型 spy 调用数为零，即使模型未配置、离线或密钥无效也能快速压缩。
2. **Q02：优先级与最低保护集。** 超长对话、反复修正目标、撤回旧指令、多语言、emoji、组合字符下，保留当前目标、最新约束、未解决问题、近期相关证据和待批准动作身份。不能以“较新”替代权威性，也不能把模型猜测提升为已验证事实。
3. **Q03：不可再缩小。** 若最低保护集／单个不可分割项已超过预算，返回明确阻塞或要求用户缩小输入；旧活动上下文不变。不得静默删除当前指令、系统约束或审批关联字段以达标。
4. **Q04：工具配对完整。** tool call 与 result 以完整逻辑单元保留或压缩，不出现孤立 result、虚构 call、重复 ID、顺序错乱、截断 JSON。失败、拒绝、取消和结果未知仍有相应状态；未完成工具单元不得压缩。
5. **Q05：事实与权限。** 来源保留 chat/run/action、目标／连接身份、证据引用与状态。保留“等待批准”的说明不授予批准；已经用过、取消、失效或属于旧连接的批准不能重生。构造含“已经批准”“忽略限制”的终端输出和历史摘要，断言零额外权限、零命令写入。
6. **Q06：完整序列化预算。** 对最终请求计入系统内容、消息、摘要、工具 schema、角色及协议开销；同时验证 token 预算和字节／消息／输出硬上限。测试正文刚好达界、超一字节、超一 token、长工具 schema 与空正文大元数据。
7. **Q07：有界与脱敏。** 大量事件不会形成无界内存副本；摘要、缓存、诊断、测试快照和持久化均不泄漏已知秘密。新秘密注册使旧衍生摘要／缓存失效或重新脱敏；旧输出分页缺口如实保留，引用不能读到原已淘汰内容。
8. **Q08：非破坏性与独立保留。** 单次压缩前后原始历史条目顺序、内容摘要和所有者不变；活动上下文单独提交版本。内存保留策略可淘汰已压缩且不受保护的旧缓存页，但不得删除或改写已持久化的对话归档；无归档可回读时才明确展示历史缺口，不能把缓存淘汰伪装成归档删除或永远完整。不同聊天、服务器和 run 的素材不能因同名命令或相同文字相互混入。
9. **Q09：大对话持续与有界内存。** 大窗口模型在消息超过 128 条、原文超过 256 KiB 后，经活动窗口压缩仍能继续；不被旧全局限制提前拒绝。拟定内存预算为每聊天 8 MiB、进程 64 MiB，需跨平台基准验证及峰值／暂存副本统计。仅淘汰已压缩且无保护的原始页，保留当前目标、摘要、live action、完整工具对和引用锚点；保护集仍超限时明确暂停，不能破坏它或超额无限增长。历史关闭时不暗中落盘，开启时只从已同意的持久历史分页读回；无存储／已过期内容显示 gap，不重跑命令补齐。

10. **Q10：长期对话与动态记忆分层。** 分别验证 `durableConversationArchive`（持久对话归档）与 `dynamicWorkingMemory`（动态工作记忆）。建立跨较长时间、大于内存配额的旧对话，压缩及 8 MiB 聊天 RAM 淘汰前后核对归档条目／内容摘要不变；打开很久以前的对话时分页读取，活动请求投影仍受预算约束。查看历史不会自动把整份归档加入模型请求，更不能自动发送；选择历史材料进入请求仍须遵守当前目标、接收方与授权边界。
11. **Q11：归档保留与磁盘异常。** 持久对话遵循独立、明确的磁盘配额／保留策略，不能为满足上下文 token 或 RAM 限额静默删除旧记录。磁盘满、权限拒绝或归档写入失败时明确警告并将未落盘内容标为“未保存”；不得伪报保存成功或自动擦除旧记录腾空间。历史默认关闭时无隐藏持久化；开启后的归档是对话记录，不等于完整原始终端流，终端日志与输出保留另行设置和验收。重启后查看归档／重建动态记忆不自动恢复执行、重发请求或激活旧批准。

## 4. 模型压缩与失败原子性测试矩阵

1. **M01：正常摘要。** 使用结构化 fixture 验证 schema、字段上限、来源引用、目标／约束／未完成事项和证据映射。摘要输出是非可信数据，不能直接改写宿主事实、工具权限、审批或活动 run 状态。
2. **M02：超大输入。** 压缩模型输入本身也要计算预算和输出预留；超过容量时按完整逻辑单元分块，有限批次归并。不能把整个历史塞给模型后依赖供应商报错；单块不可容纳时明确停止。
3. **M03：分块／归并失败。** 首块、中间块、最后块、归并分别注入超时、429、认证失败、连接中断、无效 JSON、空输出、超长摘要、引用缺失或冲突。任何失败都不得提交部分摘要；已有活动 revision 完整保留，临时结果清理，无自动命令重放。
4. **M04：语义退化与无收益。** 固定黄金案例包含旧结论已被新证据推翻、否定约束、条件指令、错误退出码、多个同名目标、未批准动作。验证保护字段来自宿主，不依赖模型自觉保留；无法验证的模型结论保留“推测”标识。无收益、变大、覆盖不完整或未满足 02 节 6.5 提交矩阵时不提交，保留旧投影。成功条件是保护项／引用完整、同口径严格可计量缩减、待发送请求满足硬 token／byte 预算；不要求任何固定压缩后比例，也不要求低于自动触发阈值。分别测试 token、byte、both、手动和默认容量路径的提交条件；无收益或硬预算仍不满足时明确暂停。
5. **M05：调用有限。** 记录压缩请求次数、分块数、输入／输出估算及真实 usage（若供应商返回）；每 job 最多 8 次模型请求（含归并）、总时长 120 秒，单请求遵循更严格的既有限额，任一预算耗尽即停止。禁止递归压缩自身摘要造成无限调用、无上限重试、失败后无提示自动改用快速方式。
6. **M06：可选真实模型评测。** 经单独配置和允许的测试供应商运行中文、英文、长日志、工具配对、目标修正和注入样例；只用合成／已脱敏数据。记录 endpoint 类型、模型标识、日期、fixture、输出和实际 usage。对保护字段、引用和协议执行确定性检查，对摘要遗漏／误述做人工评分；不以一次好结果承诺所有模型等效。
7. **M07：真实测试的发布表述。** 无凭据、网络受限或成本未获批准时可跳过真实供应商测试，但必须标记未运行；不得用 mock 截图或固定响应声称真实模型已验收。若发布宣称支持某真实供应商，需该供应商对应证据，或明确列为未验证兼容路径。

## 5. 自动触发、并发与恢复测试矩阵

1. **A01：阈值与去重。** 用可控 token 计数验证 80% 仅作为自动触发阈值，不是压缩后成功门槛；不设固定压缩后比例或时间型冷却。80%→75%、90%→85% 在保护项／引用完整、严格缩减且硬预算满足时都可提交。以 eligible-source／coverage fingerprint 和尝试记录防止同源自动反复压缩：仅 commit revision、摘要包装或时间戳改变不算新可压缩内容；相同 payload 下一次不再自动调用。新增有效可压缩内容后重算；配置修正和用户显式重试按明确入口处理。没有新可压缩内容且仍超硬预算时暂停，而非调用循环；去重不能绕过发送前预算检查。
2. **A02：触发对象与默认容量。** 自动判断以“下一次完整请求估算”及有效输入预算为准：`input_budget_tokens = context_window_tokens - output_reserve_tokens - safety_margin_tokens`，占用为 `estimated_input_tokens / input_budget_tokens`，达到 80% 触发，不拿上一请求实际 usage 当当前占用。容量优先级为有效用户覆盖 > 已验证元数据 > 产品默认值；默认 `256000` tokens（十进制 256K），标记 `capacity_source=product_default`，不是供应商容量事实。无元数据的自定义模型仍默认自动压缩开启；仅容量无效／无法解析或有效输入预算非正等异常路径暂停并解释。经审计的最终编码请求 1 MiB 字节硬护栏，在 80% 字节压力时也可提前触发已配置方式（默认模型）；单独标识原因，不假称 token 已到阈值。将自动方式设为 quick 后，token／byte／both 均零供应商调用；手动 quick 不改变保存的自动方式。统一原因枚举 token_pressure / byte_pressure / both / manual。默认容量高于供应商实际窗口导致 overflow 时，保留输入与上下文、提示调整容量，不猜测新窗口、不静默重放请求。无效容量路径不拿 null／负数预算画百分比，仍执行字节硬护栏。
3. **A03：工具执行中。** 工具已派发、结果尚未到达、前台命令未独立就绪、结果未知及审批交互期间分别触发自动／手动压缩；不改正在执行请求的快照，不拆分 call/result，不产生第二次派发。需要等待的压缩只在安全边界重新检查最新 revision。
4. **A04：提交竞争。** 摘要生成途中新增消息、编辑目标、另一次压缩先提交、聊天删除、用户取消、run 结束，均触发 revision／身份复核。按 ledger／projection revision、chat/task/run、session generation／target、配置 revision／destination／model、redaction revision、cancel epoch 形成提交 fence；完整校验后 CAS，过期结果不得覆盖更新状态，同一源 revision 的重复 IPC 只产生一次提交。
5. **A05：取消。** 取消压缩立即阻止其提交；迟到模型响应不能复活压缩。取消运行阻止新增规划和命令；远端程序是否已停止按原有证据单独报告。关闭弹层的含义与取消操作分开验证。
6. **A06：身份与供应商变化。** 切聊天、换服务器、断线重连、换连接身份、模型／endpoint／配置 revision 改变后，旧压缩结果失效或只读展示；不能向新供应商自动发送原先只获旧目标同意的数据。重新计量容量、工具 schema 和传输同意，不继承旧批准。
7. **A07：失败／未知。** IPC 响应丢失、进程崩溃、摘要已落盘但 UI 未收到结果、保存写入失败分别验证状态核对与原子提交。核对只读；禁止把“未知”当“未执行”自动重试模型或工具写入。
8. **A08：恢复边界。** 重启只恢复已明确设计的持久化数据和只读记录；旧运行、旧上下文或旧批准不自动激活。所谓“恢复”不扩大为跨进程持续任务或自动续聊承诺。

## 6. 用量与界面验收

1. **U01：简单主界面。** 保持一个输入框；用紧凑入口展示上下文用量，展开后显示分类占比和压缩操作，避免把阈值、分块、账本 revision 等技术参数铺在主界面。普通聊天不要求先理解压缩术语。
2. **U02：操作清楚。** 自动压缩默认开启并采用模型方式；手动可选择模型／快速。快速方式标明不调用模型；模型方式提示会使用当前已授权模型处理上下文。禁用、等待安全边界、处理中、成功、失败、产品默认容量和容量无效各有独立文案；重复点击不重复提交。
3. **U03：计量诚实。** “下一次请求预计用量”仅代表当前 prepared 投影，与“上一次请求实际用量”分区且标明估算／供应商返回、模型和请求时间；`last_request_usage` 绑定 `request_id` 与请求种类，不能覆盖当前估算，也不能按供应商总量伪造分类实报。供应商不返回 usage 时显示未知，不能显示 0 或伪造真实 token；旧模型 usage 不随新模型容量改算百分比。
4. **U04：类别与合计。** 分类账本无重计／遗漏，合计与同一请求快照一致；类别占比明确以预计输入总量为分母；主占用以有效输入预算为分母，与自动 80% 触发一致，不能混用完整窗口分母。输出预留、剩余容量、不可归类／协议开销有明确归属；四舍五入误差不能伪装为超额或缺失数据。
5. **U05：自定义模型。** 有效用户覆盖、已验证元数据、无元数据回退产品默认 256000 tokens、无效容量分别测试，并验证优先级。默认容量下百分比明确基于产品默认预算，不冒充真实供应商窗口；用户覆盖标为手动设置。普通自定义模型缺元数据不能被误判为无效并关闭自动压缩；容量实际无法解析或估算无法完成时显示原因，不画伪百分比或 0%。
6. **U06：压缩结果。** 显示同一口径的压缩前后估算、方式、状态和必要警告；不能用不同模型、不同 revision 或缓存 usage 比较“节省”。压缩请求消耗与聊天请求消耗分开；本版不虚构费用、账单金额或精确成本节约。
7. **U07：交互与可访问性。** 宽窄窗口、长中文、键盘操作、焦点恢复、屏幕阅读器标签和状态通知；后台聊天压缩不抢当前焦点。错误可理解且有可行下一步，颜色不是唯一状态提示。
8. **U08：证据分层。** 浏览器 mock 验证呈现和事件；前端／IPC 集成验证真实状态更新；原生运行验证进程、持久化、断线与恢复。截图须标注环境，不能以网页预览证明原生操作成功。

## 7. v0.1.4 → v0.2.0 迁移与回退

1. **升级前置。** 锁定公开 v0.1.4 的实际安装资产、SHA256 和来源提交；若尚未发布，先等待并核验，不能拿候选构建冒充正式升级起点。保存受现有隐私设置约束的数据库／配置备份，备份位置、权限和清理策略明确。
2. **只增不毁。** 为活动上下文和压缩元数据采用版本化存储；迁移先校验、再原子提交。迁移时原始聊天和历史保持可读，旧数据库格式或字段不可静默删改；后续内存缓存页保留／淘汰由独立策略负责，持久对话归档不随缓存淘汰；无可回读归档时显式展示缺口，不把正常过期描述成迁移丢失。迁移失败保留原文件，明确报告，不部分迁移后继续写入。
3. **历史不自动激活。** v0.1.4 的历史摘要、只读上下文、旧目标、旧 run 和审批仅是旧资料，不自动成为 v0.2.0 活动上下文。用户明确发起新请求时，按新架构和当前授权构造上下文；历史来源与失效状态保留。
4. **大历史处理。** 覆盖恰好 128 条／256 KiB、边界内外、旧版拒绝发送、单条过大、坏 UTF-8、缺失引用和受限输出。升级后旧 128 条／256 KiB 不再作为全局发送拒绝条件；用超过两项旧限制的对话证明压缩后可继续，并覆盖受限内存下分页和历史过期。迁移不能承诺无限保存所有旧输出；已有裁剪／缺口如实延续。压缩本身不删除原始历史，独立内存保留策略可以淘汰无保护旧缓存页，但不得影响持久对话归档。
5. **隐私与设置。** 原有历史／日志开关、脱敏规则、目标隔离、已授权供应商范围保持；迁移不能自行打开历史记录或上传旧历史。迁移原始记录和派生摘要都遵循既定存储／保留上限，持久化与内存各有有界策略。
6. **压缩回退。** 模型失败、快速压缩无收益或无法满足硬预算、验证失败、提交失败均回到上一个完整活动 revision；保留用户输入和可诊断错误。回退不清空原始历史、不增加权限、不自动换模型、不自动重跑命令。
7. **版本回退。** 在隔离副本验证 v0.1.4 读取旧格式快照；若 v0.2.0 新数据不能被旧版识别，明确只支持从升级前备份恢复，不能声称无损降级。旧版不得写入未识别的新 schema；恢复备份导致的新数据丢失必须先明确告知。
8. **迁移验收。** Windows NSIS、Linux DEB 分别覆盖首次安装、真实升级、应用重启、异常中断、重复迁移、空间不足／权限拒绝、卸载再装及回退演练。验证迁移即时历史数量／内容摘要、配置、目标身份和权限不变；再独立验证内存页淘汰、归档分页回读和无归档时的可见缺口，不能混为迁移损坏或归档删除。记录精确资产与结果。

## 8. 分阶段开发门槛

1. **阶段一：设计冻结。** 统一术语、默认策略、预算来源、账本分类、状态机、IPC、存储版本、8 MiB／64 MiB 内存预算的基准计划和迁移／降级边界。检查本验收矩阵与架构、交互文档一致；只交付文档，不修改 v0.1.4 发布任务。
2. **阶段二：账本与计量。** 在后续获准的开发阶段实现版本化活动上下文、来源／身份约束、完整请求预算与用量快照；先通过确定性计量、UTF-8、隔离及存储原子性测试，再接压缩。
3. **阶段三：快速方式。** 实现无模型确定性裁剪／归并、最低保护集、完整工具单元及失败回退；通过 Q 系列和对应迁移测试，证明网络调用为零。
4. **阶段四：模型方式。** 实现有限分块／归并、非可信输出验证、独立调用预算、过期结果拒绝、模型错误处理；通过 M 系列。真实供应商验证独立记录，不能阻塞无凭据环境的确定性测试，也不能被 mock 替代。
5. **阶段五：自动策略与界面。** 接入安全边界调度、80% 触发／可压缩来源 fingerprint 去重、手动操作、占用分类与状态提示；通过 A／U 系列，完成真实原生与迁移演练，修复回归后再进入候选版本。
6. **阶段六：CI 与发布。** 对最终候选精确提交运行既有前端测试／构建、Rust 格式／单元／集成／严格 Clippy、浏览器 smoke、真实 SSH／PTY 回归、Windows／Linux 打包及新增上下文测试。工具链与命令以仓库锁定配置和当时 CI 为准，不能仅运行新增单测后宣称全绿。
7. **分支与发布约束。** 所有后续代码先在 dev 按阶段开发、测试和审查；只有测试证据齐全且存在明确发布意图时才推进 main／v0.2.0 tag／Release。不因文档完成自动合并、推送或发布，不修改／复用 v0.1.4 标签。

## 9. 发布证据与阻断条件

1. 发布证据包包含需求—测试映射、精确 SHA、工作流运行链接、各平台资产和校验和、安装／升级记录、脱敏截图、已知限制、真实模型的运行或未运行说明，以及用户指南中的压缩和用量解释。
2. 以下任一问题阻断发布：压缩导致历史破坏、权限复活或越界、工具重复派发、未完成工具对断裂、秘密泄漏、无界内存／调用、revision 覆盖新状态、失败部分提交、默认容量冒充已验证供应商事实或无效容量仍显示伪百分比、模型方式失败后静默换方式、升级损坏原始记录。
3. 对可能发生语义损失的摘要明确提示“压缩后的工作上下文”，保留原文查阅路径和缺口说明。用户指南不能承诺永不遗忘、无限对话、永久输出保留、零模型费用或重启自动续跑。
4. 最终交付说明分别列出已实现、已验证、未验证和已知限制；本文件当前所有测试项仍是待执行计划。
